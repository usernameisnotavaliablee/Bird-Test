# 觅Ta「查询字段」转圈后无反应 · 故障诊断定稿

> 现象：2026-11-20 起，喜鹊儿 2.6.454 在「觅Ta → 按条件查找」页点「查 找」后只转圈，随后无任何反应（无弹窗、无列表、无提示）。
> 手段：静态读 454 明文 dex（`analysis/latest/plain_jadx/sources/`）+ AVD 实机跑官方包 + mitmproxy 抓包 + 响应注入实验。
> 日期：2026-11-23。结论等级：**服务端行为已实测直证；客户端行为有行号直证**。

## 0. 结论速览

| 层 | 结论 | 证据强度 |

## 1. 客户端：转圈是谁、什么时候关

- 转圈本体 = `g5/b`（MyloadProgress）→ `f9/d`（ProgressDialogNew）→ `res/layout/dialog_new.xml`（136×90dp 黑底 + `GifImageView @drawable/frame_loading_1` + 「加载中...」）。
- **show 只有 4 处，全在请求层** `da/b.java`（1813 / 1826 / 1859 / 1872，条件 `f41330d == "0"`）。六个觅Ta 入口 Activity 自身**没有任何 loading 控件**。
- **dismiss 有三处**：`da/b.java:291`（响应回调第一行）、`:416`（方法尾）、`:1463`（异常入口 `i(Exception)` 进来先 dismiss）。所以「转圈不关」只可能来自「请求没发出去」或「回调压根没回来」。
- 超时可排除：全树统一 connect/read/write 各 30s（`BaseApplication.java:1046-1048`），超时走 `i(exc)` → 先 dismiss 再 Toast「连接喜鹊儿服务器超时」。表现为**必弹提示**，与本现象不符。

### 1.1 空包是怎么被咽下去的

```
da/b.java:291    回调首行 → dismiss 转圈
da/b.java:300    BaseApplication.h() 全局闸门：只认「同时有 errcode + message」的 JSON，否则放行
da/b.java:307    仅 /wap/baseInfoServlet 与 getLoginInfoNew 做整包 AES 解密
da/b.java:358    strD 为 null 或 trim 后为空 → callbackError(new JSONException("JsonNull"))
MitaNew2Activity.java:294    public void callbackError(Exception exc) { }   ← 空实现
MitaNewListActivity.java:87  同上
```

→ 结果：转圈消失、界面零变化。这就是用户看到的「先转圈，而后无反应」。

### 1.2 其它静默分支（同源问题，非本次触发）

| 位置 | 条件 | 表现 |
|---|---|---|
| `MitaNew2Activity.java:265-291` | 回包不是 `{"result":{flag,msg,data}}` 形状 | `catch printStackTrace`，零提示 |
| `MitaNew2Activity.java:270-288` | `flag` 取值非 0/1/2 | `else` 链无兜底，既不弹也不跳 |
| `t9/t0.java:88` | `getMITA` 回包缺 `state` | `JSONException` 静默，不弹不跳 |
| `da/b.java:1801` | 同 key 1 秒内重复请求 | 直接 return，不建 dialog 也不回调 |
| `g5/b.java:87-90` | context 非 Activity / 已 finishing | 不显示转圈（「点了完全没动」的另一条路径） |

## 2. 服务端：实测证据

抓包环境：AVD 沙箱跑官方 454（已登录），mitmproxy 记全量 flow，设备代理 `10.0.2.2:8080`（app trust-all，无需装 CA）。

| flow | 请求 | 响应 |
|---|---|---|
| 1 | `wapController.jsp` 学期列表 | 200 / 110 B `{"xnxq":[{"dm":"20260",…}]}` ✅ |
| 2、4 | 同 6 的 `param` | 200 / 827 B `{"errcode":"-3","cache":{"jklist":[…]}}` |
| 3、5 | 首页数据 | 200 / ~4.7 KB 加密包 ✅ |
| **6** | **觅Ta 查找（默认条件）** | **200 / 0 B 空包体** ❌ |
| **7** | **觅Ta 查找（身份=教师）** | **200 / 0 B 空包体** ❌ |

细节：

- flow 6 与 2/4 的 `param` **逐字节相同** → 同一请求被重发三次，响应序列 `-3` → `-3` → 空。`-3` 在 `BaseApplication.h()` 里走 `hVar.a()` → `d.h()` 重发。
- flow 6 与 7 的 `param` 不同（`…2b36zn452mt0` vs `…2b37kr4p2mt0`）→ 两次不同条件的查找**都是空**。
- 空包响应头：`Content-Type: text/html;charset=utf-8`、`Content-Length: 0`，带新 JSESSIONID。
- 同会话其它请求全部有数据 → 排除登录态、网络、签名、代理问题。

## 3. 红队检验：「服务端把觅Ta 接口关了」不成立

| # | 反驳证据 |
|---|---|
| 1 | 查找仍返回 **200**。同环境对照：不存在的路径（`/wap/mitaServlet` 等）返回 **404** HTML；未加密请求返回 `{"errcode":"-2","message":"非法调用,没有加密"}`。服务端有能力表达「不可用」，但查找给的是 200。 |
| 2 | **响应注入直证身份**：mitmproxy addon 把「内容为空」的响应改写为 `{"result":{"flag":"0","msg":"REDTEAM-PROBE","data":[]}}`，再点「查 找」→ 界面弹出 `REDTEAM-PROBE`。①那条 200/0 确实是查找请求；②客户端解析链完全正常。 |
| 3 | 把 flow 6 完整请求体（含 token/param2/xqerSign/timestamp）**绕开代理直接 curl 重放** → `content-length: 875` + `{"errcode":"-5","cache":{…}}`。错误路径带结构化 body，空包不是通用行为。 |

**定性**：不是下线，是「该 action 执行后不产出数据」，且服务端选择用 `200 + 0 字节` 而不是错误码表达。

## 4. 「榨干Ta」能否曲线救国

### 4.1 请求构成（`patch/src/qx/ProbeActivity.java:255-350`）

全部走 App 自己的 `da.b`，因此 native 六元组加密与 `baseInfoServlet` 的 AES 解密都由原客户端完成，**请求形态与官方页面完全一致**。

| # | 方法 | URL | 参数 |
|---|---|---|---|
| ⓪ | GET | `{base}/wap/wapController.jsp` | `userId`=自己、`usertype`=自己、`action=getKb`、`step=skbjmc`、`skbj`、`xnxq`、`xn`、`xq`（仅课程详情宿主） |
| ① | GET | `{base}/wap/baseInfoServlet` | `userId`=自己、`usertype`=自己、`step=other`、**`otheruuid`=目标** |
| ②a | GET | `{base}/wap/wapController.jsp` | `action=getSettings`、`step=getMITAWithOther`、`userId`=自己、`usertype`=自己、`other`=目标uuid |
| ②b | GET | 同上 | 同 ②a，仅 `usertype`=对方 |
| ③ | GET | `{base}/wap/wapController.jsp` | `action=judgeBlackList`、`touserId`=目标JID、`tousertype`=对方 |
| ④ | GET | `{base}/wap/wapController.jsp` | `action=oriHd_ggym`、`step=GetTeaResume`、`userid`=去前缀、`jsid`=教师号（两个候选各发一次） |

**结构要点**：① 只吃 `otheruuid`，不吃任何搜索条件 → 它是「按 id 取人」，不是「按条件找人」。

### 4.2 返回体（历史真机实测）

| 请求 | 实测返回 |
|---|---|
| ① 教师目标（陈磊 / 10475_10250137） | **18 键宽行**；`state=0`（对方未开觅Ta）**仍下发** 姓名/性别/学校/部门/账号，另带 `msg=人力系统未对接`；`xueli/xuewei/gangwei/zhichen/jg` 键在值空 |
| ① 学生目标 | 18 键，含 `xm/xb/xxdm/xh/uuid/ssbj` |
| ② `getMITAWithOther` | `state` + 隐私门 `msg`，与 ① 的 `state=0` 自洽 |
| ③ `judgeBlackList` | `flag`（0=正常，非 0=拦截） |
| ④ `GetTeaResume` | 某次 `{"resultSet":[]}`（该校未接人事系统）；另一 jsid 候选未定论 |
| ⓪ `getKb&step=skbjmc` | `{"classmatesList":[21 条]}`，字段 `yhxh/xm/xb/bjmc/yxb/bj/zy/yxbmc/zymc/nj/njmc/tags/pycc/pyccmc/uuid` |

### 4.3 分层结论

- **能救**：手里有目标 uuid/JID 时，① 能拉该人信息，且**绕开客户端觅Ta 开关判定**（`state=0` 服务端照样下发，已实测）。「已知某人 → 看 ta 的信息/课表/名单」这条链完好，与坏掉的查找无依赖。
- **救不了**：查找的职责是「条件 → uuid 列表」。榨干Ta 不发搜索请求、也不解析搜索响应，没有替代品。
- **uuid 来源（已存在、合规）**：收藏/关注 `guanxin&step=course_shoucang_me`、看过我的 `course_chakan_me`、同班名录 `getKb&step=skbjmc`、扫码 `hqsf xqxt|<uuid>`。都是「已在关系/班级内」的人。
- **合规红线**：uuid 形如 `xxdm_学号`，学号可猜 → 枚举等于批量拖库，本项目明确不做。曲线救国的上限：**救已知 uuid 的人，救不了按条件发现陌生人**。

## 6. 未解项与下一步

1. **action 明文名未知**：`param` 为 native 加密串，`t9/q0` 在 release 里全是空方法（`LogUtil` 的 a~f 全部空体）。要定名需 Frida hook `NDKTools.getStringFromNDKZDY`。不影响结论。
2. **服务端为何不产出**：可能是内部异常被容器吞成空响应、数据源为空、或该分支未实现。需要服务端日志，客户端侧无法再推。
3. **AVD 现状**：重装 probe 包后 App 启动即 `exit(0)`（14 秒 206 次，`mCurrentFocus=null`）；已排除 GPU（`-gpu guest` 同样）、`/system` rw/ro、su 缺失三种诱因。若要继续动态验证，下一步应抓 `zprotect` 解包之后第一个 `System.exit` 的调用栈，或改用真机。
