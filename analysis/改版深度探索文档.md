## 探索结论速览

1. **觅Ta 开关是纯客户端校验**：篡改后确实能展示对方数据（课表/信息/同学列表），但**黑名单拦截、自身/对方觅Ta 双开关校验、TEA 身份旁路、同校校验均仍生效**——绕过的是"对方未开启觅Ta 开关"这一层客户端拦截，而非所有权限门禁（见 §1.5 残留门禁清单）。
2. **第三方 SDK 零改动**：推送 appkey、百度/华为 key、assets/res 配置全部与底包 byte-identical，18 个差异文件全为反编译噪声。
3. **签名绕过 = ApkSignatureKillerEx**：Java 伪造 `PackageInfo.CREATOR` + native xhook 重定向 `open` + LSPosed HiddenApiBypass，骗的是运行时自检而非安装校验；注入方式是**改 BaseApplication 超类**（manifest 的 application 仍写 BaseApplication）。
4. **重大新发现（数据窃取）**：改版者注入 `mt.Log22A16D`（唯一被激活的窃密组件），把**4 处解密后的明文密码** + 3 处密码密文 + **每次点击同学时的姓名/班级/性别 PII** 落盘到 `/sdcard/MT2/logs/`（明文、无加密、无轮转）。
5. **觅Ta 门禁新增第 6 处**：`a2/a.java` 的"由于对方设置【觅TA】隐私开关，您无法查看其信息"拦截也被掏空。
6. **Log 类审计**：7 个 `mt/Log*` 中 **6 个是改版注入**（仅 `Log22A16D` 被调用激活，其余 5 个休眠/诱饵），`LogD78843` 是**底包自带**且休眠（字节与内嵌底包一致）。
7. **无其它监控组件**：除签名绕过 + 觅Ta 绕过 + Log22A16D 本地落盘外，**未植入**远程回传、截屏、剪贴板、键盘、无障碍、网络 hook 等收集组件（`b9/a.java` 截屏 ContentObserver 为底包自带业务功能）。

## 一、觅Ta 服务端调用链（客户端校验，篡改有效）

### 1.1 完整调用链

```
用户点击"查看他人信息"
  └─ TeaInfoActivity.g.onClick / ClassmateInfoActivity 内部类
       └─ a2.a.e(ctx).j(ctx, userId, userType, otherUuid, "TEA"/"STU")
            │  发 judgeBlackList 预检（黑名单）
            │  POST http://api.xiqueer.com/manager/wap/wapController.jsp
            │     action=judgeBlackList, userId, usertype, touserId, tousertype
            ├─ 若黑名单 → 弹"已加黑名单，不能查看个人信息！"
            └─ 若通过 → 进入 person-info 流程

a2.a.k()/l()  发 person-info 请求
  │  GET http://api.xiqueer.com/manager/wap/baseInfoServlet
  │     step=other, otheruuid=<对方uuid>, userId, usertype
  └─ 响应 JSON：xm(姓名), xb(性别), uuid, mita, headavatar...
       └─ 回调 h9.b.f 实现类（TeaInfoActivity$j / ClassmateInfoActivity 等）
            └─ mita = 对方是否开启【觅Ta】开关（服务端下发）
                 └─ mita=="1" → 刷新同学列表 / 展示课表
                 └─ mita!="1" → 弹"未开启【觅Ta】服务，无法查看ta的信息"（原版）

另：TdkbActivity / MitaNewActivity / MitaNewListActivity
  └─ 响应 state=="1" 判定觅Ta 开关 → 跳转 TaWeekCourseActivity（y8/g.a）
```

### 1.2 关键端点

| 端点 | 参数 | 用途 |
|---|---|---|
| `/wap/wapController.jsp?action=judgeBlackList` | touserId/tousertype | 查看前黑名单预检 |
| `/wap/baseInfoServlet?step=other` | otheruuid | **他人完整信息**（含 mita 开关） |
| `/wap/wapController.jsp?action=getSettings&step=getMITAWithOther` | other | 查对方觅Ta 开关状态 |
| serviceUrl 默认 | `http://api.xiqueer.com/manager/`（SharedPreferences `serviceurl` 可覆盖） | 全局 API 基址 |

### 1.3 决定性验证：篡改后能否拉到数据？

对比两版 `a2/a.java` 的 `k()/l()/a()` 请求构造——**请求参数完全一致**（仅混淆字段 `f42801a→f42819a` 编号偏移，URL/参数名/值来源相同）。

结论：
- `mita`/`state` 是**服务端在 person-info 响应里下发的字段**，表示"对方是否开启觅Ta"。
- 服务端 `baseInfoServlet?step=other` **不看调用方是否已开启觅Ta**——只要带 `otheruuid` 就返回完整数据。开关限制完全由**客户端弹窗**实现。
- 改版把 `if(mita=="1"){刷新}else{弹窗}` 掏空成 `if(...){}` 无条件刷新后，**服务端照常返回数据，篡改确实生效**。
- 结论：**纯客户端校验，无服务端强制**。改版后能展示未开启觅Ta 开关同学的数据（见 §1.5 精确范围）。

## 三、签名绕过完整机制（ApkSignatureKillerEx）

### 3.1 注入组件

| 组件 | 说明 |
|---|---|
| `bin/mt/signature/KillerApplication` | 注入入口，**改 BaseApplication 超类**注入（manifest 的 application 仍为 BaseApplication） |
| `lib/libSignatureKiller.so`（arm64-v8a / armeabi-v7a / armeabi） | native 层路径 hook |
| `assets/SignatureKiller/origin.apk`（64,853,894 字节） | 内嵌真实底包（含原证书） |
| `org/lsposed/hiddenapibypass/*` | HiddenApiBypass 隐藏 API 绕过 |
| `mt/Log22A16D` 等 **6 个注入 Log 类**（另 1 个 `LogD78843` 为底包自带） | 日志/数据记录组件（**见 3.4**） |

### 3.2 三层机制

**① Java 层：伪造 `PackageInfo.CREATOR`**（`killPM()`）
```java
// 硬编码原版 KINGOKEB 证书（Base64），反射替换静态字段：
findField(PackageInfo.class, "CREATOR").set(null, new Creator<PackageInfo>(){
    createFromParcel(parcel) {
        PackageInfo pi = origCreator.createFromParcel(parcel);
        if (pi.packageName.equals(pkg)) {
            pi.signatures[0] = kingokebSig;          // v1 签名
            if (SDK>=28) pi.signingInfo.getApkContentsSigners()[0] = kingokebSig;  // v2 证书
        }
        return pi;
    }
});
// Android 9+：HiddenApiBypass.addHiddenApiExemptions("Landroid/os/Parcel;","Landroid/content/pm","Landroid/app");
// 清缓存：PackageManager.sPackageInfoCache / Parcel.mCreators / sPairedCreators .clear()
```
原理：`getPackageInfo()` 是 app→system_server 的 binder IPC，system_server 把 `PackageInfo` 序列化为 Parcel，app 进程反序列化时调用 `PackageInfo.CREATOR.createFromParcel()`。替换 CREATOR 后，app 进程内**看到的目标包签名被伪造为原版证书**。

**② Native 层：xhook 重定向 `open`**（`killOpen()` + `hookApkPath()`）
- `System.loadLibrary("SignatureKiller")` → 扫 `/proc/self/maps` 定位真实 base.apk → 解压内嵌 origin.apk 到 `/data/data/<pkg>/origin.apk` → `hookApkPath(real, origin)`
- native（xhook 1.2.0 静态链接）注册 **4 个 hook**：`openat / openat64 / open64 / open`，作用域 `.*\.so$`（全部已加载库的 PLT/GOT）
- 替换桩：`strcmp(路径, realBase.apk) == 0` 时把路径改写为 `origin.apk`，再转跳原函数
- **目的**：让 native 代码直接 `open()` 读 base.apk 做二次校验时，读到的是**未篡改、用原证书签名的底包**——和 Java 层伪造互为补充。

**③ HiddenApiBypass 原理**
- 用 Unsafe 求 ART 内部偏移（artMethod 槽大小、methods 数组偏移），手工遍历类的方法/字段表
- `revealDirect` 反查隐藏 `Member`；用"永远 throw 的桩方法" `InvokeStub` 把 artMethod 改成目标隐藏方法再调用
- `setHiddenApiExemptions` 绕过限制调 `VMRuntime.setHiddenApiExemptions(签名前缀)`
- 解锁的 API：`android.os.Parcel.mCreators`、`sPairedCreators`、`android.content.pm`、`android.app` 内部成员

### 3.3 哪层被绕过、哪层没被绕过

| 校验层 | 执行者 | 是否被绕过 |
|---|---|---|
| 安装期 v1 校验 | system_server（改版包用 ANDROID 证书自洽 v1 签名） | **否**（作为新应用安装通过） |
| 安装期 v2/v3 | — | 不适用（两 APK 均无 v2/v3 块） |
| 升级/同签名校验、signature 权限 | system_server 用真实证书(ANDROID)判定 | **否** |
| 运行时 `getPackageInfo()` 签名 | app 进程 | **是**（CREATOR 伪造） |
| native 直接读 APK 文件自校验 | app native 代码 | **是**（open 重定向） |
| 服务端上报签名 hash | 业务服务器 | 部分（取决于上报值来源） |

**关键**：这套机制**不能骗过安装期系统校验**（重打包包以 ANDROID 证书安装），骗的是**应用运行时的自我认知**。因此：
- 不能覆盖安装原版（INSTALL_FAILED_UPDATE_INCOMPATIBLE），需先卸载
- signature 级权限/系统 API 会拒绝（证书是 ANDROID）
- 局限：只 hook open 系；`stat/faccessat`/已缓存 fd 不受覆盖；带 v2/v3 的 APK 需额外重签

### 3.4 数据窃取注入（重大发现）

`mt.Log*` 日志类**不是签名绕过的辅助**，而是改版者植入的**监控/数据收集组件**。经四路复核，精确结论如下：

#### 3.4.1 唯一激活的窃密组件：`mt/Log22A16D`

**实现**（`mt/Log22A16D.java`）：
- 线程模型：`extends Thread`，静态块 `setDaemon(true)` + `start()`（L21-25），无界 `LinkedBlockingQueue` + `ThreadLocal` 参数缓冲（L18-19），首次被调用点触发即后台常驻。
- 落盘路径：`/sdcard/MT2/logs/com.kingosoft.activity_kb_common-<时间戳>.log`（外部存储），追加模式，失败自动回退 `/data/data/<pkg>/logs/`（L353-373）。
- 格式：`[TIME] [CLASS] ->[METHOD]([LOCATION]) [RESULT]`，**明文、无加密**（`Charset.defaultCharset()` 写出）、**无轮转/清理**、**无任何网络/POST 代码**。

**注入点与记录内容**（内嵌底包对应文件 0 处调用 → 全部为改版注入）：

| 注入点 | 记录内容 | 证据 |
|---|---|---|
| `y8/j0.java`（PersonMessage 用户信息，classes3.dex） | **4 处解密后明文密码**（L71/153/229/331，`f9.a.b(SharedPreferences "pwdStr")`）+ **3 处密码密文**（L134/209/312，`f9.a.c()` 加密值） | 7 处 `Log22A16D.a()`（smali 层 invoke-static 逐一核实），内嵌版 0 处 |
| `b8/b.java`（同学列表适配器，classes2.dex） | **每次点击同学回调**记录**他人**姓名 `xm`、班级 `bjmc`、性别 `xb`（经 `w2.a.a` 去 `]` 前缀） | 3 处 `Log22A16D.a()`（L88/97/100），内嵌版 0 处 |

**密码解密完整链**（`f9/a.java`，底包原有，改版只注入日志调用）：
```
f9.a.c(pwdStr)     加密   AES/CBC/PKCS5Padding  key=loginkeyapp93214  IV=12fg45gpsdfz34ab  → 存 SharedPreferences "pwdStr"
f9.a.b(pwdStr)     解密   URLDecoder → Base64.decodeBase64 → AES/CBC 同 key/IV → 明文密码
改版在 f9.a.b() 结果处插入 Log22A16D.a() → 明文密码落盘 /sdcard/MT2/logs/
```
> 密钥/IV **硬编码**在 `f9/a.java`（与底包一致），拿到日志文件即可还原明文、直接登录用户账号。

#### 3.4.2 Log 类三分类（改版 vs 内嵌底包）

| 分类 | 类 | 落盘路径 | 全库调用方 | 激活状态 |
|---|---|---|---|---|
| **注入·激活** | `mt/Log22A16D` | `/sdcard/MT2/logs/...` | `y8/j0` 7 处 + `b8/b` 3 处 | **正在窃密** |
| **底包自带·休眠** | `mt/LogD78843` | 同 Log22A16D | 0（改版与底包均无） | 休眠（md5 与内嵌底包一致，非注入） |
| **注入·休眠** | `mt/LogE0E388` | `/sdcard/MT2/logs/...` | 0 | 休眠/诱饵 |
| **注入·休眠** | `mt/Log25EB87` `Log5A0B53` `LogA704BA` `LogBE294D` | `/sdcard/<pkg>-<ts>.log`（sdcard 根） | 0 | 休眠/诱饵 |

> 全部 7 个类同模板（`extends Thread` + static init + 落盘），仅类名/路径不同；7 个均来自 classes.dex。

#### 3.4.3 暴露面评估

- **路径**：`/sdcard/MT2/logs/` 位于**共享外部存储根目录**，非应用私有目录。改版与底包 manifest 均声明 `MANAGE_EXTERNAL_STORAGE` + `requestLegacyExternalStorage`（权限为**底包原有**，改版利用之，非新增权限）。
- **谁可读**：任何获 `READ_EXTERNAL_STORAGE` 的应用（API≤32）、获"所有文件访问"（API 30+）、ADB/USB 主机、文件管理器。配合改版声明的 `QUERY_ALL_PACKAGES` + 签名绕过栈，可被共置恶意应用静默拉取。
- **生命周期**：时间戳建文件 + 追加写，**无轮转/清理/删除**，持久留存。
- **回传**：全工程 grep 未发现读取该日志或 POST 上行代码 → 当前为**纯本地落盘**，回收途径是物理/USB/共置应用，而非服务器回传。但**明文密码 + 硬编码密钥**使拿到文件即可直接登录账号。

**风险评估**：明文密码（4 点）+ 同学 PII（每次点击即写）落盘外部存储 → 可被其他应用读取；配合签名绕过批量分发重打包 APK 后回收本地日志 → **脱库/撞库准备**。敏感等级：极高。

1. **安装**：改版包以 ANDROID 证书自洽 v1 签名安装（须先卸载原版）
